# 22. 最重要的一条设计原则

我非常建议你从一开始就规定：

> **AI 只能“解释证据”，不能凭空创造活动。**

例如：

```text
Evidence:
VS Code
foo.ts
keyboard active
git diff

↓ AI

"coding"
confidence 0.97
```

而不是：

```text
VS Code
↓
AI:
"你正在认真开发一个复杂的系统"
```

后者很容易变成“AI 自嗨式时间管理”。

你的系统应该始终允许：

```text
AI判断
   ↓
证据
   ↓
用户纠正
   ↓
模型/规则改进
```

最终甚至可以做：

```text
用户：
“这 30 分钟不是摸鱼，我是在研究。”

        ↓

Activity Correction

        ↓

以后：
类似 URL / 标题 / 行为
→ 更容易识别成 research
```

这样它会逐渐成为一个**真正了解你的个人时间系统**，而不是一个截图监控器。

如果按你现在的技术栈继续往下做，我认为下一步最值得讨论的是 **“Windows 上到底能采集哪些信号 + 每种信号的成本/准确度 + 如何组合成 Activity Segment”**。这个部分决定了整个项目 80% 的架构，我可以直接给你设计一版具体的 **Collector → Event → Activity Engine → SQLite 数据结构和算法**。

# 二、第一原则：Event 是最底层事实

假设你 10:00 打开 VS Code。

Collector **不要**产生：

```json
{
  "activity": "coding"
}
```

而应该产生：

```json
{
  "type": "window.focus",
  "timestamp": 1759284000123,
  "payload": {
    "process": "Code.exe",
    "title": "activity-monitor - main.ts"
  }
}
```

因为：

> VS Code ≠ coding。

同样：

```text
Chrome ≠ browsing
YouTube ≠ entertainment
Discord ≠ chatting
Word ≠ working
```

**语义判断必须留给 Activity Engine。**

# 四、Event 最好分成“状态事件”和“瞬时事件”

这是很容易踩坑的地方。

例如：

```text
10:00:00 VS Code 获得焦点
10:15:00 Chrome 获得焦点
```

这里不是说：

```text
VS Code 只使用了 1 个事件
```

而是：

```text
VS Code active
10:00 ─────────────── 10:15
```

因此：

### 状态型

```text

system.idle
system.resume
media.play
media.pause
```

### 瞬时型

```text
git.commit
file.change
browser.navigation
input.activity
```

这个区分非常重要。

```text
       │
       ▼

10:17 Chrome
```

# 六、不要轮询写数据库

Collector 可以：

```text
100ms / 500ms / 1s
```

检查系统状态，但：

**不要每次检查都写 SQLite。**

只有状态变化才产生 Event。

例如：

```text
轮询：

10:00:00 VS Code
10:00:01 VS Code
10:00:02 VS Code
10:00:03 VS Code
10:00:04 VS Code
```

最终：

```text
10:00:00 window.focus VS Code
```

就够了。

# 七、Input Collector 也不要记录“按了什么键”

你真正需要的是：

```text
有没有活动
活动强度
```

而不是：

```text

用户按了 B
用户输入了密码
```

所以：

```ts
interface InputActivity {
  keyboardEvents: number
  mouseEvents: number
  mouseDistance?: number
}
```

例如每 10 秒汇总：

```text

keyboard = 87
mouse = 31
```

形成：

```json
{
  "type": "input.activity",
  "timestamp": 1759284010000,
  "payload": {
    "keyboard": 87,
    "mouse": 31
  }
}
```

这样隐私风险会低很多。

# 十七、第一版甚至不用机器学习

可以直接：

```ts
function similarity(a, b) {
  let score = 0

  if (a.app === b.app) score += 0.3
  if (a.project === b.project) score += 0.3
  if (a.category === b.category) score += 0.2
  if (a.domain === b.domain) score += 0.2

  return score
}
```

这非常重要：

> **先用确定性规则把系统跑起来，再让 AI 接管“不确定部分”。**

# 二十九、Bucket 算法

例如：

```ts
function getBucket(timestamp: number, interval: number) {
  return Math.floor(timestamp / interval) * interval
}
```

假设：

```text

```

```text

```


然后：

所以：

# 三十、Activity Merge 算法

假设 Engine 连续收到：

```text
10:00 coding
10:05 coding
10:10 coding
10:15 coding
```

不要生成：

```text
4 activities
```

而是：

```text
10:00 ───────── 10:20
       coding
```

伪代码：

```ts
function merge(previous, current) {
  if (!previous) {
    return current
  }

  const gap = current.startAt - previous.endAt

  const sameContext =
    previous.category === current.category &&
    previous.application === current.application &&
    previous.project === current.project

  if (sameContext && gap < GRACE_PERIOD) {
    previous.endAt = current.endAt
    previous.confidence =
      (previous.confidence + current.confidence) / 2

    return previous
  }

  return current
}
```

实际实现可以更复杂一点。

```text
几百万条
```

其实 SQLite 也可以扛，但没必要永远保留所有原始细节。

---

# 三十七、SQLite 写入也要做 Batch

千万不要：

```ts
event → INSERT → COMMIT
```

每个事件一次事务。

而应该：

```text
Memory Queue

Event
Event
Event
Event
Event
 ↓
100ms / 500ms
 ↓
BEGIN
INSERT × N
COMMIT
```

例如：

```text
collector
    ↓
in-memory queue
    ↓
batch writer
    ↓
SQLite
```

这样可以显著降低磁盘唤醒。

---

# 三十八、甚至 SQLite 都不需要每个 Event 立即落盘

可以：

```text
高频：

Collector
 ↓
RAM queue

低频：

100~1000 events
 ↓
SQLite transaction
```

但有一个原则：

> **程序正常退出时 flush。**

异常情况下允许丢失最近几秒的非关键 Event，换取更低的 IO。

这对“个人时间统计”完全合理。

---

如果目标是：

> **电脑开一天，不希望这个程序自己变成耗电大户**

那么我会设：

### 常驻

```text
Window monitoring

Input activity aggregation
```

成本：

```text
非常低
```

### 条件触发


### 低频

```text
OCR

```

### 极低频

```text

```

### 用户主动

```text

Agent review
```

最终：

```text

    ↓
几十/几百 bytes
    ↓
Rule Engine
    ↓
绝大多数事件直接结束
    ↓
只有少数不确定事件
    ↓

```

这会比：

```text

→ AI
```

高效很多。

# 四十、我建议你的第一版数据库实际上只做 5 张表

不要一开始把数据库做复杂。

```text
┌────────────────────┐

└────────────────────┘
```

`browser_events`、`git` 等可以**先作为 Event 的 payload**，等你真正遇到查询性能问题再拆表。

# 四十一、我甚至会把整个 Engine 做成纯函数式的核心

这是你这个项目非常适合的架构：

```ts
const nextState = reduceActivityEngine(
  previousState,
  event
)
```

例如：

```ts
const state = {
  currentSegment,
  currentContext,
  session,
}
```

输入：

```ts
event
```

输出：

```ts
{
  state,
  actions,
  activities
}
```

这样：

```text
真实电脑
     ↓
Events
     ↓
Activity Engine
```

和：

```text
历史 Events
     ↓
Activity Engine v2
```

可以得到完全不同的结果。

这意味着以后你升级：

```text
Classifier v1
```

到：

```text
Classifier v2
```

可以直接：

> **重放过去 30 天的 Event → 重新计算 Activity。**

这个能力会非常强。

# 四十二、最终我会把项目的核心对象关系定成这样

```text
Event
 │
 │  observed
 ▼
Context
 │
 │  classified
 ▼
Activity Segment
 │
 │  bucket
 ▼
Time Block
 │
 │  aggregate
 ▼
Daily Summary
 │
 │  analyze
 ▼
Agent Insight
```

具体就是：

```text
Event
"VS Code became foreground"

        ↓

Context
"VS Code + activity-monitor + segmenter.ts
 + keyboard active + git modified"

        ↓

Activity
"coding / activity-monitor / Activity Engine"

        ↓

Time Block
"10:00-10:30 → coding 27m"

        ↓

Daily
"coding 6h42m"

        ↓

Agent
"今天主要完成了 Activity Engine，
但下午存在较多上下文切换。"
```

而最重要的是：

**Agent 最后一层不能反过来污染前面的事实层。**

也就是说：

```text
Agent：
“我觉得你下午效率不高”
```

绝对不能修改：

```text
Event
Activity
```

最多变成：

```text
Insight
{
  type: "observation",
  claim: "...",
  evidence: [...]
}
```

这样整个系统会非常干净。

## 我认为最值得你下一步直接实现的是这个 MVP

```text
Windows
  │
  ├── Foreground Window
  ├── Idle
  └── Input Activity
          ↓
      Event Bus
          ↓
       SQLite
          ↓
   Activity Engine
          ↓
     30min Timeline
```

**先完全不接 AI、不截图、不浏览器扩展。**

等这条链跑起来后，再加：

```text
Browser Extension
        ↓
URL / Title
        ↓
Rule Classifier
```

然后才：

```text
Unknown
   ↓
Screenshot
   ↓
Local VLM
```

这样你不会一上来就陷入“AI 到底怎么判断我在干什么”的泥潭，而是先建立一个**可靠的个人时间原始数据层**。

而且这套架构非常适合你现有的 **pnpm monorepo + TypeScript + SQLite** 思路：`activity-engine` 可以完全独立于 UI，未来 Vue/React 两套 Dashboard 都只是消费者。
