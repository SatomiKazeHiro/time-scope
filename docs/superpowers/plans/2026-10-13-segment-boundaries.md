# 计划：把「段的时间边界」收敛到一处

**状态**：待执行 · **写于** 2026-10-13 · **基线 commit** `4d84bdb`（Rust 386 / 前端 351，全绿）

---

## 为什么要做这件事

起点是用户报的现象：「昨天专注度 100%、24h 时段分布几乎满柱」。
查下来发现那**不是两个 bug，是四个**，而四个是同一个病：

| 现象 | 直接原因 |
|---|---|
| 一天凭空多出 18 小时 | `extend` 无条件 `end_at = max(ts)` |
| 全库 95 分钟被数两遍 | `merge_into` 无条件 `start_at = min(...)` |
| 引擎产出重叠段 | 同上 + `absorb` 复活跨过已释放段 |
| 「浏览 30 分钟」显示高度专注 | 「单一类别」被当成「专注」（另一件事，见 §4） |

**共同点：段的时间边界没有唯一的所有者。**

`src-tauri/crates/engine/src/segmenter.rs` 里有 **6 处独立地写 `start_at` / `end_at`**，
每一处自己决定往哪边取 min/max：

| 行 | 函数 | 写法 | 会不会越界 |
|---|---|---|---|
| 274 | `fold_short_segments` 的 open 分支 | `o.start_at = min(...)` | 会（往前撑） |
| 311-312 | `merge_into` | `start_at = min` / `end_at = max` | 会 |
| 377 | `absorb` | `prev.end_at = max(ts)` | 会（往前跨已释放段） |
| 402-403 | `new_open_segment` | `start_at = ts; end_at = ts` | 否（正确起点） |
| 438 | `extend` | `cur.end_at = max(ts)` | 会（空档守卫在 448，438 没走） |
| 448-453 | `close_current` | 守卫已加 | 已修 |

代码里**已经写着**「不可凭空造时间」这条原则（`fold_short_segments` 附近的注释），
但守卫只加在了 `close_current` 一处 —— 另外 5 处都能违反它。

**这就是为什么重叠查了三轮都查不完**：不是某一行写错了，
而是「边界归谁管」这个问题从来没有被回答过。

---

## 目标（做完之后世界是什么样）

1. **段的边界只有一个所有者。** 任何代码要改 `start_at`/`end_at` 都必须经过
   `Segment` 的方法，方法内部保证不变式。
2. **不变式写在类型里，不在注释里。** 现在那句「不可凭空造时间」是注释，
   改成编译期/测试期的约束。
3. **有一条全局不变式测试**：「任意两条段不得重叠」，它对整天的段成立，
   不依赖任何特定路径。
4. **读侧不必再替引擎擦屁股。** `clip_to_uncovered`（去重）退化为兜底，
   而不是必需 —— 它现在承担着引擎该做的事。

**不在本次范围内**：改数据库 schema、重放历史数据、动 `daily_calendar` 的 SQL
（这些留到 §4 的合并轮次）。

## 执行步骤

### 步骤 1：先钉住不变式（**不改任何生产代码**）

给 `crates/engine/src/tests/segmenter.rs` 加一条：

```
段两两不得重叠 —— 对一整天的真实事件流成立
```

要求：用**合成数据**（不是真实库），覆盖 `extend` / `absorb` / `merge_into` /
`fold_short_segments` 四条路径。目的是「任何改动之后，这条都得是绿的」。

**✅ 执行结果（2026-10-13，已提交）**：
测试写好了（`segments_of_a_whole_day_never_overlap`，6000 个事件 / 100ms 间隔），
**但是绿的** —— 合成数据复现不出重叠。试过 20000 个事件（94 秒）仍绿。

**这本身是有价值的信息**，不是失败：
说明真实重叠依赖合成数据里没有的某个条件（真实库里有真实的窗口标题序列、
真实的切换节奏、真实的 `system_idle`）。所以这条测试的定位要改：

- **它不是「复现 bug 的测试」，是「防止未来引入重叠的护栏」。**
- 它的价值在于：做完步骤 2–3 之后它必须**仍然绿** —— 如果收敛边界时引入了新的
  撑大/跨过行为，它会立刻红。
- 想让它今天就红，需要真实数据；而真实数据不能进单元测试（那是另一个 crate
  的集成测试，且依赖本机文件）。**取舍：接受它当前是绿的，把「真实数据验证」
  放在步骤 4。**

运行时 13.5 秒偏长（引擎的 `pending` 排序是 O(n²)）。已在计划里记下，
步骤 2 收敛边界时如果顺手能减小 pending 规模就一起做，否则维持 6000。

### 步骤 2：引入边界方法（本次的核心）

**✅ 已完成（第一步：收敛 `extend` 与 `close_current`）**

在 `segmenter.rs` 里落下收敛点，只有两个函数：

```rust
pub fn crossed_observation_gap(last_evidence_at, ts, config) -> bool
pub fn advance_end(end_at: &mut i64, last_evidence_at, ts, config)   // 唯一允许往后推边界
pub fn ranges_overlap(start, end, other_start, other_end) -> bool
```

`extend` 与 `close_current` 都改调 `advance_end`。

**顺带修掉一个真实的口径不一致**：`extend` 原来是**裸的 `end_at = max(ts)`**，
空档守卫只加在 `close_current` —— 也就是说「不凭空造时间」这条原则，
在这两条最主要的路径上只有一条守住了。现在两条都走 `advance_end`，
`extend` 也拿到了它本来该有的守卫。

**387 个 Rust 测试全绿，没有一条旧语义被破坏。**

**真实数据验证（步骤 4 的前半，2026-10-13）**：
```
day         segs  overlaps  total_h    span_h
2026-10-04    262       15    22.34    22.12
2026-10-10    299        9    16.84    16.76
2026-10-12     64        2     5.72    23.98
```
**重叠数与收敛前一致**（15 / 9 / 2），时长也没有明显损失。

**这说明什么（重要）**：重叠**不是** `extend` 造成的。
`extend` 造成的是「凭空造时间」（已修，见 commit 74dc175 与本次）。
重叠另有来源 —— 就是探针查到的「两个应用各自开段撞车」，
落在 `absorb` 复活与 `merge_into` 的 min/max 上，**还没动**。

### 步骤 2b：继续收敛 `absorb` 与 `merge_into`（未做）

按同样的方式改这两处，并在动手前用 `ranges_overlap` 做前置检查。
**这一步是真正会消掉重叠的那一步** —— 但如上面所测，
它必须解决「两个应用各自开段」而不仅仅是「撑大越过邻居」，
所以预计要配合一次探针定位，不能照搬 extend 的改法。

### 步骤 3：把 5 处写边界改成调方法

逐一改，每改一处跑一次全量 Rust 测试。顺序按风险从低到高：

1. `merge_into`（已被我改过一次，风险已知）
2. `fold_short_segments` 的 open 分支
3. `close_current`（已有守卫，改造成调方法）
4. `absorb`
5. `extend`（最热，最后改）

### 步骤 4：验证真实数据

用真实库重放几天，确认：
- 段两两不重叠（重叠数应为 0）
- 全天总时长 ≤ 24h（不靠读侧去重）
- 时长没有明显损失（不能为了不重叠而吞掉真实时间 —— 差值应在原本
  「重叠虚高的 95 分钟」量级，不是几小时）

**验收标准**：重叠 0、总时长合理、386 个测试全绿。

## §4：什么时候做「专注度 migration + 剩余项」的大轮次

**触发条件（写死，避免「以后再说」）**：当下面**同时**满足时，一次做完这几件：

1. 你有**连续一个下午**的空闲 —— 这几件都要重放历史验证，不能碎片时间做
2. 步骤 1–5 已完成且全绿（**边界先收敛，再加字段**，否则两次改同一个类型）
3. 决心已定：`focus` 的分母要不要排除「人不在」

**那一轮一起做的清单**：

- **专注度 migration**（给 `ActivitySegment` 加「有活动时长 / 无输入时长」两个字段，
  `focus` 的分母从「非 idle 时长」改成「有活动时长」）。
  判据已经有数据支撑：看视频时心跳 0 与非 0 **交替**（报 0 比例 14–74%），
  但**从不连续 300 秒** —— 这正是区分「人不在」与「在看视频」的信号。
  代价：schema migration + 引擎 + 前端，历史数据回溯不了。
- **`daily_calendar` 去重**（热力图每格，现在还没去重 —— 是本轮的有意留口）
- **重放历史 activities**（修掉库里已有的 84 处重叠；只修引擎不会改旧数据）

**如果不做这一轮**：读侧去重已经让所有**用户看到的数字**正确了。
剩余的只是原始数据不够整洁、以及专注度那一栏对「一边看视频一边工作」的人会说谎。

## §已知困难（下次接着做时先看这里）

- **合成用例复现不出真实重叠。** 试过 absorb 复活、merge_into、open 分支三条路径，
  每条都能写出让它变红的测试，但**真实数据重放的重叠数一点没降**。
  真实触发条件是**事件密度**：10-10 那段 77 分钟里有 4117 个事件
  （3505 条 window_title_change + 464 心跳 + 148 focus）；
  时间戳整体拉长 20 倍就不复现，2 倍/5 倍仍复现。
- **10-10 的重叠对零证据交集。** 两条段没有任何共同的证据却重叠，
  说明是「两个应用各自开段撞车」，不是「一段盖住另一段」。
  `absorb` 复活只是其中一条路径。
- **探针方法**（下次定位用）：在 `reduce` 每步之后检查「已释放的段之间是否出现重叠」，
  第一次出现时打印当时的 `pending` 快照与本步释放的段 —— 那一刻就是成因。
  比读代码推断可靠得多（我前面三次推断全错）。
