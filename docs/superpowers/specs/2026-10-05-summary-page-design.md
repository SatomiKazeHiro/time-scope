## 1. 目标与动机

Phase 1 三步已完成，应用能采集 → 分类 → 时间线展示**某一天**。它回答的是
「我今天/昨天在干什么」。但它不回答另外三个问题：

1. **我今天总共监控了多久、活跃多少、分类构成是什么样？** 现在要自己数色块。
2. **长期看我的作息稳不稳？哪几天根本没碰电脑？** 时间线一次只看一天，没有跨度的视图。
3. **这段时间我的注意力在哪些窗口上？** `get_segment_titles` 只对**选中的单个段**生效，
   没有排名、没有横向比较。

这三件事是同一类问题：**现有界面只有「日」这一个尺度**。汇总页提供
「日 / 周 / 月 / 全部」四个尺度，顶部指标随选中范围变化，热力图作为导航图。

### 1.1 成功标准

- 侧边栏点「汇总」能进，页面三段布局与 spec 一致
- 热力图按 GitHub 贡献墙的布局渲染（7 行周日→周六、1 列 = 1 周、月标签浮在列上方），
  首列补齐到周日，跨月列数不等也能对齐
- 点格子 → 选中该日；点格子下方的周条 → 该周；点月标签 → 该月。选中范围用
  **跨格的一整块矩形**框出来，框外不压暗
- **热力图不随选中变化**。它永远是「从第一天到今天的全部数据」，只取一次
- 顶部六个指标随选中范围重新计算，24h 分布条同步变化
- 窗口标题排名经归一化后 Top 8 是可读的（不是 Edge 标签组计数器）
- 脱敏标题在汇总页仍带 `redacted` 标记（隐私标记不因换页面丢失）
- `cargo test --workspace` / `pnpm test` / `pnpm build` /
  `node design-system/time-scope/verify-palette.mjs` 全绿

### 1.2 明确不做

- **不做年视图**。默认范围是「全部」（首个有数据的日子 → 今天），列数由数据跨度决定，
  5 天是 2 列、一年后自动是 53 列。「年的设计」是一个待定的常量策略，不在本文定。
  列宽、gap、7 行结构写成常量，以后改一处。
- **范围 chip 只做 UI，不接功能**。顶栏那个「范围：全部 ▾」这一轮是死控件，
  点它没有反应。真实范围切换全部由热力图上的点击驱动。
- **范围不写 URL、不持久化**。刷新回「全部」。这是单机桌面应用，不是可分享的网页。
- **不引入 d3 / 任何图表库**。圆环、热力图、24h 条全部手写 SVG。
  实测引入全量 d3 会让产物从 262 KB 涨到约 540 KB，而圆环只是 4 个弧段。
- **不建预聚合表**。窗口标题排名走现算（§3.3），慢了再加，那是局部改动不是重构。
- **不做 `get_config` / `set_config`**。那是设置页的独立缺口（§4.2 已知限制），
  本轮不碰。
- **不改 schema**。不动 `SCHEMA_VERSION`，不加列（§3.4 有一条已知的 DST 代价）。

## 3. 数据接口

三个命令，**按数据成本分层**。实测依据见 §3.5。

### 3.1 `get_daily_calendar() → DailyCalendar`

热力图的**唯一**数据源。无参数。

```ts
interface DayCell { date: string; totalMs: number }   // totalMs = 当日全部段时长之和（含 idle）
interface DailyCalendar { first: string; last: string; days: DayCell[] }
```

`days` 覆盖 `[first, last]` 的每一天，**无记录的日期也返回 `{ totalMs: 0 }`**——
前端要靠「日期连续」才能把格子排进正确的周列，缺一天就整列错位。

SQL 两条：`SELECT MIN(...), MAX(...)` 取 `first` / `last`，
以及 `SELECT date(start_at/1000,'unixepoch','localtime') d, SUM(end_at-start_at)
FROM activities GROUP BY d` 取有记录的日期。**空缺日期由前端补**
（`src/lib/summary.ts` 的 `fillDays` 纯函数）。

补在前端而不是 SQL，因为热力图要的是**连续的日期序列**——
`GROUP BY` 会跳过没活动的那几天（比如没开机的那天），
直接用它的结果排格子会整片错位。补出来的那些天 `totalMs = 0`，
在墙里画成轨道色（§5.2）。

### 3.2 `get_summary(from: String, to: String) → Summary`

顶部全部指标，**半开区间 `[from 00:00, to+1 00:00)`**，边界复用现有的
`date_range::day_range_ms`（它已接受 `offset` 参数，单测可固定时区）。

```ts
type DonutKey = "work" | "browsing" | "idle" | "unknown";

interface Summary {
  totalMs: number;        // 监控总时长 = 全部段之和
  activeMs: number;       // 非 idle 之和
  idleMs: number;         // idle 之和
  segmentCount: number;
  switchCount: number;    // 见下
  hourlyMs: [number; 24]; // 该范围内非 idle 时长按本地小时切 24 桶
  donut: Array<{ key: DonutKey; ms: number }>;   // 恒为 4 项，见 §6
  topApps: Array<{ name: string; ms: number }>;
}
```

**`switchCount` 定义**：相邻两个活动段之间间隔 ≥ 5 分钟，记一次切换。
这与时间线指标模式的「切换次数」是**两个不同的东西**——后者是分桶后每桶内的
切换数（`src/lib/metrics.ts` 的 `bucketMetrics`）。本项是全范围不分桶的总数。

阈值**固定 300_000 ms**，不读 `config.toml`。理由：`idle_threshold_s` 改的是
「多久算空闲」，会改变哪些段被归成 idle，进而改变段本身；让两个指标耦合在
一个可调参数上，改一次配置会让两个数字的历史不可比。

`hourlyMs` 的切法：逐段按小时边界劈开累加，跨小时的段分给两桶。
Rust 侧算，不在 SQL 里（`strftime('%H', ...)` 用的是 UTC）。

`topApps` 取前 5，`application IS NULL` 的段丢弃。

### 3.3 `get_top_titles(from, to, limit) → TopTitles`

**懒加载**——底部「窗口标题 Top」面板进入视口或被展开时才发这一发。

```ts
interface TopTitles {
  items: Array<{ title: string; hits: number; redacted: boolean }>;
}
```

两段式，避免把全量行拉进内存：

1. SQL 先按**原始** title 分组（`GROUP BY json_extract(payload,'$.window_title')`），
   实测 5 天约返回 1000 行
2. Rust 侧逐行归一化（§4）后合并计数，取 top `limit`

**归一化必须在 Rust 侧**。放前端会让同一个归一化值散成多行，合并不了。

**不设范围上限，任何范围都实算。** 代价随数据量线性增长：
实测 5 天（50,461 事件）199ms，带单日范围过滤时 21.7ms；
按每天 10,092 事件外推，**一年约 3.7M 行 → 约 15s**。

这是本 spec 最贵的一条路径，且**成本落在最常见的路径上**——默认范围就是「全部」，
所以第一次打开页面滚到底部就会触发它。当前 5 天数据下 199ms，感觉不到；
一年后才会显形。届时修法是局部的（按范围键做结果缓存，或加 §9 说的预聚合表），
不是重构。**规模阈值大约在 3 个月（≈90 天 / 900k 事件 / 3.5s）**，到那时重新评估。

`redacted` 复用 `titles.rs` 里现成的判定（含 `PLACEHOLDER` 即为 true），
不重新实现占位符检查。

### 3.4 按天分组与时区

`get_daily_calendar` 用 SQL 的 `date(start_at/1000,'unixepoch','localtime')` 分组。

**这依赖进程时区，且在夏令时切换日会差一小时**（多算/少算一小时，无报错）。
这是**跟随全项目现有的假设**：`date_range::local_offset()` 返回单个
`UtcOffset`，`day_range_ms` 也用它算一天起止。给汇总页单独做 DST 正确的分组，
会制造「只有汇总页对、其他页错」的不一致。

代价写进 §8 已知限制，不隐藏。修它需要给 `activities` 加一列 `local_date`
（schema 迁移 + 回填 + 写入路径），是独立的一项。

### 3.5 成本实测（2026-10-05，本机真实库）

| 层 | 数据源 | 当前规模 | 单次实测 | 年外推 |
|---|---|---|---|---|
| 便宜 | `activities` | 458 行 / 5 天 | GROUP BY 毫秒级 | ~33k 行/年，仍是毫秒级 |
| 贵 | `events` + `json_extract` | 50,461 行 / 5 天 | 全表 199ms；单日范围 21.7ms | ~3.7M 行/年 → **约 15s** |

七个指标里六个在便宜层。**贵层只有窗口标题排名一项**，因此只有它需要懒加载
（它不在首屏；见 §9 第 7 条的成本）。

## 4. 窗口标题归一化

原始标题排名的 Top 6 **全是同一个东西的变体**（实测 2026-10-05）：

```
无标题 和另外 31 个页面 - 个人 - Microsoft Edge    1316
New Tab 和另外 31 个页面 - 个人 - Microsoft Edge   1274
无标题 和另外 32 个页面 - 个人 - Microsoft Edge    1099
◐ 项目与 uv Python 管理                             1049
◑ 项目与 uv Python 管理                             1024
无标题 和另外 33 个页面 - 个人 - Microsoft Edge     913
```

Edge 的折叠标签组标题带计数器（`和另外 31/32/33 个页面`），计数器每变一次
就算一条新标题。`◐` `◑` 是 uvicorn 的状态字符，同理。**这个排名统计的是
「计数器变过几次」，不是「你在看什么」。**

实测：1021 个唯一标题 → 归一化后 563 个（**降 45%**），Top 8 变成
`无标题` / `New Tab` / `项目与 uv Python 管理` / `DeepSeek 开放平台` /
`查看现状交接文档 — DeepSeek Harness` …

### 4.1 规则（四条，硬编码，不做配置）

按顺序应用：

1. 删掉 `和另外 \d+ 个页面`
2. 删掉**前导**状态符 `[\s◐◑◒◓●○◉*+!-]+`
3. 删掉尾部 ` - (个人|工作|私人)$`（Edge 的配置文件名）
4. 连续空白压成一个，去首尾的 ` -·:`

真实代码标题必须**原样不动**：`main.rs - Visual Studio Code` → 自身。
规则 2 只吃前导，规则 3 只吃尾部，中间的 ` - ` 不碰。这条要有一条专门的回归测试。

### 4.2 归一化救不回的部分

- `无标题`（7086）+ `New Tab`（3722）占了大头，是 Edge 空白页，信息量约等于零。
  **它们是真实存在的时间，但反映不了工作内容。** 不特殊处理，如实显示。
- `⏳ 待处理 · 了解该项目概况` 的 `⏳` 在**中间**而非前导，规则 2 吃不到。
  这类漏网的会随着应用行为变化而变化，不为它加规则。

## 5. 热力图布局算法

GitHub 贡献墙的形状。逐条定死，避免实现时凭印象：

### 5.1 网格

```
firstSun = first 之前最近的周日（first 本身是周日则等于 first）
lastSat  = last  之后最近的周六
days     = firstSun .. lastSat 的完整日期序列
weeks    = days 按 7 个一组切
```

- **7 行，index % 7**：0 = 周日 … 6 = 周六。**第一行是周日。**
- **1 列 = 1 周**，自周日起
- 超出 `[first, last]` 的格子**不渲染**（保持透明），但**占位保留**——
  否则首列和末列会错位
- 每月**第一次出现**的那一列，在该列上方写 `MMM`
- 下一个 `MMM` 至少隔 4 列才画（GitHub 的做法），避免窄窗口下标签叠在一起

### 5.2 编码

**格子的值是「当日监控时长」**（`DayCell.totalMs`，含 idle）。

5 档色阶，分档阈值是**相对当前 `DailyCalendar` 最大值**的固定比例
（0.25 / 0.5 / 0.75），不是绝对小时数——绝对值随用户的真实时长变化，
相对分档让低使用率用户也能看出深浅。图例标出每档对应的小时数
（按当前 `max` 换算，四舍五入到 0.1h）。

> 这三个比例是**初值，不是定论**。相对分档意味着「有记录以来最高的那天」
> 永远是最深档——如果实际看着觉得拉伸过度（中等的一天也顶到最深），
> 调的是这三个数，不是改成绝对阈值。**用眼睛看真实数据再定**
> （§8.4 的人工验证里包含这一步）。

**色值走 `--color-scale-1..5`（紫色阶）**，不是蓝。热力图编码的是连续量，
连续量在本项目里一律用紫色阶（MASTER §2.5 时间线指标模式已在用）。
**蓝相是类别色**——MASTER §2 把它留给 work/study，
且明确记着「类别模式和指标模式互斥，永不同框，蓝和紫色阶 ΔE 仅 0.9–2.5」。

`totalMs === 0` 的格子（补齐进来的日期——那天没开机，或装了但没活动）
用 **`--color-surface-2` 轨道色**，与 MASTER §2.5「没有活动的桶不画，
露出轨道色」同一处理：
0 活跃就该看起来是空的，不该占用一个颜色档位。

超出 `[first, last]` 的格子（不在数据范围内的补齐位）**完全不渲染**，透明。

### 5.3 交互

| 点哪里 | 得到什么 |
|---|---|
| 格子 | 该日 |
| 格子下方 4px 的周条 | 该列 7 天 |
| 月标签 `MMM` | 该月首末日 |
| 已选中的同一目标 | 取消，回到「全部」 |

悬停出 tooltip：日期 + 监控时长。

**选中框是跨格的一整块绝对定位矩形，不是逐格描边。** 日框 1 格、周框 1 列、
月框跨 N 列（N 因月份而异，2 月 4 列、31 天月 5 列）。**框的宽度本身就
告诉用户当前是哪一档**，不用读文字。

**框外不压暗。** 试过聚光灯方案（框外降到 26% 不透明度），远处月份的对比度
会跌破 MASTER 的 3:1 红线。只描框，远处保持可读。

### 5.4 待定的常量

列宽、格间距、7 行结构是常量，**年视图的策略也是常量**（默认按数据跨度）。
以后定年视图只改这一处。

## 6. 圆环

**固定 4 类**，环是完整的 360°：

| key | 含义 | 颜色 |
|---|---|---|
| `work` | 工作 | `--color-cat-work` |
| `browsing` | 浏览 | `--color-cat-browsing` |
| `idle` | 空闲 | `--color-cat-idle` |
| `unknown` | 未分类 + 学习 + 娱乐 + 社交 + 生活 | `--color-cat-unknown` |

后四个类别**并入 `unknown` 那一档**。当前数据里它们都是 0，看不出差别；
`rules.toml` 一改就会有。标签就叫「未分类」，不假装那四类不存在。

中心写**监控总时长**（`totalMs`），右侧图例四行，各带时长和百分比。

**明确不采用**的两版（记录理由，避免以后重提）：

- **8 类全画** —— 对 `rules.toml` 任何改法都成立，但图例里会有 4 行 `0.0h`，
  看着像坏了
- **3 层级 + 无活动**（沿用 MASTER 的色相编码）—— 跟时间线同一套语言，
  但「无活动」会占到 52%，圆环有一半是灰的

实现是 4 个 `<circle>` + `stroke-dasharray` + `stroke-dashoffset`，
`transform="rotate(-90 …)"` 从 12 点起。**不引入 d3**。

## 9. 已知限制

| # | 限制 | 影响 | 什么时候值得修 |
|---|---|---|---|
| 1 | **DST 地区按天分组差一小时** | 一年里 2 天的热力图格子深浅偏移 | 用户不在 UTC+8 时；修法见 §3.4 |
| 2 | **未分类占 38%**（20.6h / 54.0h） | 圆环最大一块是灰色；数字不好看 | 扩 `rules.toml` 后自动变化 |
| 3 | **标题排名不覆盖「在哪个页面」** | 只有进程内窗口标题 | Phase 2 浏览器扩展 |
| 4 | **`无标题` / `New Tab` 占标题排名大头** | 空白页真实存在但反映不了工作内容 | 不值得修，如实显示 |
| 5 | **年视图未设计** | 列数策略是待定常量 | 有 ≥ 3 个月数据后 |
| 6 | **范围 chip 是死控件** | 顶栏那个下拉点了没反应 | 范围变多（季 / 年 / 自定义）时才需要 |
| 7 | **标题排名不设范围上限，成本线性增长** | 默认范围就是「全部」，所以这条路最常走。当前 5 天 199ms；一年约 3.7M 行 → **约 15s** | 约 3 个月（900k 事件 / 3.5s）时重新评估；修法是局部的（结果缓存或预聚合表），不是重构 |
| 8 | **强杀应用当天数据可能不完整** | 当天数字偏低 | 沿用 Phase 1 spec §8.1 的既有取舍 |

## 10. 关键裁定

| 裁定 | 原因 | 代价 |
|---|---|---|
| 热力图**用紫色阶** `--color-scale-1..5`，不用蓝 | 蓝是类别色（`work`/`study`）；MASTER §2 记着蓝与紫阶 ΔE 仅 0.9–2.5、两种模式永不同框。连续量一律走紫色阶 | 无 |
| 热力图 0 档用 `--color-surface-2` 轨道色 | MASTER §2.5「没有活动的桶不画，露出轨道色」——0 活跃就该看起来是空的 | 0h 的格子不像「有值」，那正是要的效果 |
| 热力图**固定不动**，点击只选范围 | 用户明确要求「从始至终怎样就是怎样」；热力图是导航器不是视图 | 无法「放大看某个月」——要看得切到时间线 |
| 默认范围 = 全部，不是今年 | 用户明确「年的设计还没想好」；列数随数据跨度自动变 | 5 天数据下只有 2 列，看起来很空 |
| 选中框只描框，**不压暗** | 聚光灯会让远处月份跌破 3:1 对比度（MASTER 红线） | 焦点靠框的位置，不用亮度对比 |
| 选中框是**跨格整块**，不是逐格描边 | 框宽本身就表达日/周/月三档 | 实现要在墙外层算绝对定位 |
| 24h 分布条 = **24 根细柱**，不用平滑面积 | 平滑曲线会在两个 0 之间鼓出弧，读起来像「凌晨 6 点在用」——插出了数据里不存在的值 | 柱状不如曲线柔 |
| 24h 条在「全部」下是平线，**不特殊处理** | 平是诚实结果；一点某天就有波形 | 「全部」时这一条信息量低 |
| 圆环固定 4 类，其余并入未分类 | 用户「先简单的来」 | 丢掉了 学习/娱乐/社交/生活 的区分 |
| 标题归一化在 **Rust 侧** | 前端归一化会让同一值散成多行，合并不了 | 后端要维护一份正则 |
| **不引入 d3** | 全量 d3 让产物 262 KB → 约 540 KB，而圆环只是 4 个弧段 | 圆弧数学自己写 |
| **不改 schema**，跟随固定 offset 假设 | 全项目已建立该假设（`day_range_ms` 同款）；单做 DST 正确会制造不一致 | DST 地区差一小时 |
| 三个 IPC，标题**懒加载** | 六个指标走 `activities`（毫秒级），只有标题贵 | 多两个 IPC 调用和一个 loading 态 |
| 标题排名**不设范围上限**，任何范围都实算 | 用户决定「查全部」。当前 5 天数据下 199ms 感觉不到；一年的 15s 记进 §9 第 7 条 | 一年后首次打开页面滚到底部会等约 15s；届时加结果缓存或预聚合表 |
| **不建预聚合表** | YAGNI；慢了加表是局部改动 | 大范围下标题排名会慢（§9 第 7 条） |
| 归一化规则**硬编码四条**，不配置 | 规则是我猜的；做成配置等于让它变成「用户要去维护的东西」 | 换应用要改代码 |
